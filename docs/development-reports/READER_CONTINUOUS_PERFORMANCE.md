## 本轮有证据的改进

### 连续翻页后的 PDF 绘制资源

旧实现删除离屏 canvas，但 PDF.js 的 PageProxy 仍保留绘制指令与已解码对象。现在在页面离开预读窗口、渲染取消结束后调用公开的 `PDFPageProxy.cleanup()`。当前页和邻页继续保留；快速返回、缩放或切书时检查资源归属，避免清理新的渲染。缩放仍可复用当前页资源，不每次都清空整本 PDF。

在 348 页真实组成原理 PDF 的副本中串行对照，连续跳转 20 个位置，每处相隔 6 页，共触达 120 页（含邻页预读）：

| 指标 | 调整前 | 调整后 |
| --- | ---: | ---: |
| 仍保留绘制状态的页 | 120 | 6 |
| 离屏仍保留绘制状态的页 | 114 | 0 |
| 保留的绘制操作条数 | 31941 | 1578 |
| 跳页至绘制的中位数 | 68ms | 66.5ms |

返回最初页面正常重绘，截图已检查。上述是一次短时连续阅读模拟，不能代替几小时使用测试。浏览器总工作集没有显示稳定降低（末尾约 1057 / 1095 MiB，返回后约 1056 / 1077 MiB），所以不宣称已经降低多少实际内存，或解决了所有内存增长。已证实的收益是离屏显示资源不再随访问页数一直保留。

计数仅在测试页面检查 PDF.js 内部状态，产品只用公开 cleanup API。`reader-first-open.mjs` 的 `READER_FIRST_LIFETIME=1` 可复测；`READER_FIRST_LIFETIME_PAGES` 控制停留点数，`READER_FIRST_APP_SOURCE` 仅用于对照旧的测试脚本副本。测试数据在结束后删除，结果与截图保留在临时目录。

### 滚动时不重复排版笔记

旧路径每个 scroll frame 都重建本页标记列表，即使 Notes 隐藏，AI 保存回答也重新进行 Markdown / 公式排版。现在页码、阅读会话、标记数组和面板开关没有变化时保留原 DOM；关闭时只更新计数，不构建隐藏回答。

对一条 AI 保存回答的 120 次同页更新，原来创建 1800 个 DOM 节点、排版 120 次；现在隐藏时不构建正文，显示时只构建一次。新增、更新、删除、切页及同书重开仍刷新；没有改标记保存方式。

### 冷习题整理不阻塞保存

冷 Practice catalog 原来在派生缓存的全局锁内构建，所有数据库写事务提交也使用这个锁。隔离真实 607 题样本中，整理需约半秒；并发保存阅读位置的 SQL 本身约 2ms，提交却要等 489–582ms。

现在构建和结果复制放在锁外，锁内仅做短时间的版本检查、失效与发布。同一场景的提交等待降至 0.31–0.85ms。此项单独调整没有加速 catalog 本身，后续的提取优化见下节。仍覆盖写入中的旧快照、外部连接、回滚、同 key 并发、嵌套与失败。为保持简单，同时 miss 可以各自计算；写入期间的旧计算可以返回给原读取请求，但不能发布为新缓存。没有新增缓存表或更改事务保存语义。

### 冷习题整理约快 4 倍

原来构建 catalog 时，整本书每行 OCR 的字符框和坐标都先做 JSON 解码；多数正文、解析行根本不用字符框。现在只在题目入口和选项命中区需要时解码字符框，行边界同样按需计算并复用。不改变识题规则、题号、正文、选项、区域或答案。

四本真实教材串行做 3 轮新旧对照，中位数如下；共 2090 道题的完整内部对象逐题相等。

| 教材 | 调整前 | 调整后 |
| --- | ---: | ---: |
| 操作系统，523 题 | 550ms | 127ms |
| 计算机网络，476 题 | 416ms | 113ms |
| 数据结构，484 题 | 584ms | 133ms |
| 组成原理，607 题 | 484ms | 140ms |

### 滚动时减少重复扫描与布局

- 读取当前页面位置，由整本书全扫描改为对当前 DOM 边界做二分查找；不维护另一套容易过期的页面坐标。
- 目录当前项没变时不逐项设置 class / aria，也不重复 scrollIntoView；换书、重建目录、明确要求显示当前项时仍更新。
- 文字层进度实际没变时不反复写工具栏 DOM；重连、重试和本页进度仍即时刷新。

同一台 Edge、同一本书，120 帧同页微滚动，串行 ABBA 对照：updateViewport 累计脚本时间从 163–171ms 降至 22.5–27ms。4 倍 CPU 降速模拟中，目录关闭/打开分别从 676/711ms 降至 112/104ms，目录同步从约 100ms 降至 1.9ms。真实机器原本的帧时间已较健康，因此不宣称帧率提升 6 倍；CPU 降速模拟也不等于另一台真实电脑。

回归覆盖同页 subsection 边界、5.4.2 点击后的固定落点、继续滚动、非等高页、缩放和学习区脚注变化；位置结果与旧全扫描一致。

### 长阅读的 OCR / 标记缓存有上限

PDF 绘制资源清理后，另一个增长来源是整本书曾访问页的 OCR 字符框与标记快照。现在各保留最近约 24 页；当前页、当前选区、正在绘制和预读窗口内的页受保护。它们都是可重新读取的显示缓存，SQLite 标记和原 OCR 没有删除。

同一本书跳转 40 处、触达 240 页：对照版保留 OCR 240 页、标记约 205 页，JS 堆约 25.2 MiB；最终产品代码保持各 24 页，JS 堆约 8.4 MiB。访问约 60 页后堆大小维持在约 8.4–8.8 MiB。返回旧页确认原书像素、文字层和已保存标记重新加载。浏览器总工作集仍未出现可靠下降，不将 JS 堆改善写成进程总内存改善。

### 搜索只为真正命中的文本算来源位置

旧实现对全书每个字符都建立归一化后的来源偏移表，并解码命中页所有行的字符框。现在先按原规则归一化查找，只为命中范围回算来源位置、解码相交行的字符框。文本、覆盖率和命中位置仍来自同一个只读事务。

四书常用词搜索的中位数由 166–231ms 降至 72–105ms；无命中由约 145–170ms 降至 70–90ms。共 40 组完整响应严格相等，覆盖跨行、Unicode 多字符展开、大小写、空白、页数上限及精确选字位置。limit=3 原本只需扫少量页，没有稳定收益，不宣称所有查询都快一倍。

### 流式回答合并同帧滚动

Assistant / Master 仍即时追加每段文本，不缓冲正文，不改 Provider 或生成过程；只将同一帧多次读取 scrollHeight / 设置 scrollTop 合并为一次，并检查取消、换书、退出和对话归属。Master 完成时处理最后一次待滚动，保持最终正文可见。

真实轻量 Edge 样本，6092 字、200 个 chunk、每帧 8 个 chunk：两处 scrollHeight 读取均从 200 次降至 25 次，最终文字一致且位于底部。正常分散到达的网络流收益有限；没有将仅追加阶段的计时当作总 CPU 提升。

### 顺带修正标记旧请求的会话边界

检查缓存恢复时，复现了既有问题：普通标记保存请求发出后立即重开同一本书，旧响应仅检查 revision，会再次插入已读取的标记、清除新选区。普通保存、删除、Assistant 保存、审查重试与轮询现在都核对本次 Reader generation，过期响应不修改新会话，也不显示旧失败或重启轮询。真正重开 Reader 时重置共用保存按钮；旧请求不能解锁新会话进行中的保存。同书已打开的提前返回路径不重置按钮。原请求是否已在 SQLite 保存由服务端结果决定；没有改变保存语义。

### 晚到布局不误关选区菜单

最后一轮阅读 smoke 曾在颜色展开后超时。进一步延迟真实 Learning 响应，确认是实际时序问题：页脚晚到使滚动偏移增加 449px，浏览器锚定却保持所选文字的屏幕位置完全不变；原滚动监听仍把高亮/笔记菜单关掉。

现在菜单打开时记住所选原文的视觉位置。滚动事件发生时，原文没有实际移动就保留菜单；原文移动、缩放、换选区或来源失效仍收起。不改 Master 布局，也不禁止真实滚动。真实延迟响应复现通过：布局补偿后菜单保留，用户再滚动 120px 后正常关闭，重新右键并保存高亮成功。没有靠延长测试等待掩盖问题。

## 为什么在这里停止

- 默认 CPU OCR 的两页真实剖析中约 88% 时间在 ONNX 推理；排序约 1ms、JSON/哈希不足 1ms。继续微调周边代码收益很小；更换推理后端涉及内存、兼容性与坐标一致性，独立实验保留，不自动变为默认。
- 搜索剩余主要是必要的文本读取（约 42–44ms）和归一化扫描（约 13–29ms）；继续减少需要额外全书缓存或索引。当前规模不值得为几十毫秒引入另一套生命周期。
- catalog 的公开 JSON 投影和序列化约 3.5–5.5ms，复制约 12–22ms。进一步减少复制会增加可变对象共享风险，暂不改。
- 小书库的 Master / Memory 查询没有测出值得新增索引或迁移的等待；不增加迁移、缓存表或后台管线。
- Assistant 另测 10 轮、每轮约 4000 字和 2 个公式的长历史：首次冷挂载含布局约 157ms，后续新增/切换/保存约 36–40ms，同一视图更新约 0.4ms。首次仍有可感知短任务，但新增历史缓存不能消除冷挂载；为此引入增量排版与选区失效规则成本更高，留作确有长对话使用反馈时的候选。
- 浏览器原生比较仍未取得有效书页图像，不宣称追平。结果仅适用于本机真实教材和所测路径，不表示所有设备都没有进一步空间。

本轮连续翻页后返回、目录高亮、Notes、搜索、习题整理和流式回答优化已通过人工验收；首屏优化的通过状态一并保留。当前安装版 Desktop 未更新，本次 GitHub 同步不代表安装包已发布。剩余候选的收益和风险已不适合继续堆改动，停止性能扩展，没有后台定时任务。

## Desktop 0.4.13 集成回归：Practice 并发加载

首屏与连续性能优化已在 `bf6d27d` 收口。随后 Desktop 集成的真实 Practice smoke 发现，从 Learning Memory 点击“继续复盘”偶发无法进入。

原因是延后的 Reader 后台加载与 Memory 显式等待同时调用 `loadPracticeRecords`。旧实现每次递增 epoch，先返回的请求被后发调用作废，却让先调用者的 await 正常结束；此时 catalog 还没发布、习题集合仍为空。epoch 在重开同书时又从零开始，也不能隔离旧会话响应。

最小共享修复：

- 同一 Practice 对象共用一个在途 Promise，完整应用 catalog、记录和继续位置后才结束；不将 `catalogReady` 当永久缓存，完成后的再次调用仍刷新。
- 使用 Reader generation、revision 和 Practice 对象身份隔离换书 / 同书重开；旧结果、失败与 finally 不影响新会话，Memory 等待后也再次核对归属。
- OCR 完成通知排队串行重读；GET 直接发现全部 READY 和 SSE 完成使用同一刷新入口。普通并发调用不会重复发起相同读取，必要刷新不会被吞掉。
- 继续等待位置保存队列；读取期间若追加了新保存，等保存完成再读最新位置。练习进行中的 catalog 仍放到 `pendingCatalog`，当前题和位置保持。

确定性 VM 回归覆盖并发调用和逐响应完成、旧空 catalog 与刷新、直接 READY 状态、同书重开 / 换书、保存等待 / 中途保存、活动题目、失败重试及 Memory 过期回调。相关 Node 检查 33 项通过，其中 10 项为新增加载回归；JS 语法与 diff 检查通过，没有跑全量测试或调用真实 AI。

真实教材离线 smoke 已通过，增加受控等待 catalog / 记录响应：原页绘制完成且延后的后台上下文已加入后，仍只有一组在途读取，Memory 不提前进入；释放后恢复指定收藏题与已有 Master 对话。首次新增探针的 glob 未匹配嵌套 catalog 路径，导致测试等待挂起；改为精确端点正则并增加有界等待后重跑通过，未用延时绕过产品竞争。此项不改变先前两组优化的人工验收时间。没有改 OCR、官网、Practice UI 或 Desktop 打包；本修复独立提交，Desktop 合入后需要全新重建和集成验收。
