# Reader 性能调查

2026-10-22。覆盖导入、资源释放、PDF 显示、Practice、搜索、学习状态、AI 本地准备、侧栏、后台任务和存储。本轮新增调查工具与报告，未修改产品功能、提交、打包或发布。

后续状态：用户已授权优化，以下保留调查时的基线与实验结论；当前实现和复查结果见 [Reader 通用性能优化](READER_PERFORMANCE_OPTIMIZATION.md)。原 PDF destroy 注入参数已移除，调查脚本直接测试产品释放逻辑。

## 结论与顺序

最值得先做的改进集中在资源释放和重复计算，不依赖独立显卡，也不需要降低清晰度。

| 顺序 | 问题 | 本机证据 | 建议 |
| --- | --- | --- | --- |
| 1 | 关书没有释放 PDF 加载任务 | 五轮打开后 worker 为 5；四次关闭后仍依次保留 1、2、3、4 个 | 统一处理加载中退出、切书、失败及正常关闭的资源释放 |
| 1 | PDF 校验把整份文件复制进内存，并等待 GC 释放 | 同组四次校验，峰值 482 MiB；文件流并及时关闭的实验为 41 MiB，页面元数据一致 | 管理文件流和 PdfReader 生命周期 |
| 2 | Practice 查一题仍重建全书习题 | 重复全书提取约 630–780ms；现有按节提取约 12–70ms，对照三节结果一致 | 复用按节提取，减少重复查题，按来源变更复用结果 |
| 3 | 学习状态重复推导整书显示位置 | 单次约 125–168ms，约 1.9 万次 JSON 解码；profile 中约 91% 时间在显示位置计算 | 分开统计摘要和几何投影，复用未变化的位置结果 |
| 4 | 搜索为每个命中页重新连接数据库 | 100 页命中约 102 次连接；同组约 650ms，单次读取连接实验约 250ms，结果一致 | 合并为一次操作内的读取，保留现有文字归一化与定位规则 |
| 5 | 高缩放、高 DPI 的邻页画布开销 | DPR 1 / 400% 与 DPR 2 / 200% 均约 360 MiB 的 RGBA 尺寸容量 | 按像素预算决定邻页预绘制范围，保持当前页清晰度 |

这些对照证明优化方向有价值，还不是已经完成的产品修复。端到端收益需在正式实现后验证。

## 测量条件

- Windows，Ryzen 7 8845H；现有 Edge / Chromium，1440×1000 窗口，分别测 DPR 1、2。不是低配电脑、独显或其他 CPU 的横向评测。
- 使用真实书库的一致性 SQLite 备份及 PDF 副本，原书库不写入。书库有 4 本、1436 页、约 7.7 万行 OCR、574 个 KP；浏览器主要使用 348 页组成原理教材。
- Practice 的该书完整提取结果为 27 节、607 道符合当前规则的题。导入对照另使用两份约 146 MiB 的真实 PDF。
- 基础操作大多重复三次。profile 会引入计时开销，只有带 profile 的调用用于分析耗时归属；普通调用用于比较时延。未运行全量测试，未发起付费 AI 请求。

## 1. PDF 的资源生命周期：优先处理

`static/app.js` 每次打开调用 `getDocument()`，关闭时取消渲染、清空画布并把 `state.pdf` 置空，但没有保留、销毁 `PDFDocumentLoadingTask`。

在同一浏览器里五次打开同一本书、到 PDF 51 页、退出：

- 打开后的 worker：1、2、3、4、5。
- 四次关闭后的 worker：1、2、3、4；主页面强制 GC 后仍存在。
- 第五次打开时，新建浏览器各进程工作集加总约 2018 MiB。

仅向隔离浏览器提供一份实验版 app.js：保留 loading task，关书时销毁它；没有编辑产品 app.js。相同操作中，每次打开为 1 个 worker，每次关闭回到 0，四次销毁均成功。第五次打开工作集加总约 1035 MiB。

工作集加总包含共享页重复统计，不等于精确独占物理内存。两组证实了资源累积及可行的释放入口；打开耗时约 1.2–4 秒且波动明显，不能将所有延迟波动归因于这一项。

本项目 PDF.js 为 6.3.289，实测释放入口是 **loading task 的 `destroy()`**；不能照旧示例对 document proxy 调用 `destroy()`。正式实现还应覆盖加载尚未完成时退出、快速切书、过期 promise 返回和失败后的清理，保持阅读位置与学习状态。

## 2. 导入与 PDF 校验：主要机会在内存

`library/service.py::_validate_pdf` 直接将路径传给 PdfReader。本版本 pypdf 会读取整份文件进内部流；函数结束没有显式关闭 reader，内部对象可能留到 GC。

同两份文件各校验两次，三个独立进程对照：

| 实验 | 峰值工作集 | 四次结束后的工作集 | 校验耗时范围 |
| --- | ---: | ---: | ---: |
| 原实现 | 482 MiB | 482 MiB | 86–110ms |
| 原路径方式，结束时显式关闭 | 187 MiB | 41 MiB | 99–114ms |
| 使用文件流并显式关闭 | 41 MiB | 41 MiB | 64–86ms |

四次页面元数据哈希完全一致。这是未及时释放造成的瞬时内存积累，没有将其描述为永久泄漏。完整导入的另一组带 profile 测量中，工作集在四次导入/重复导入后到约 557 MiB，GC 后回到约 120 MiB，也支持这一判断。

重复导入目前还会先完整解析 PDF，再查已有 hash。已有可靠重复来源可减少重复解析；上传、哈希、落盘仍有必要。正式修复须继续覆盖损坏文件、加密、异常页尺寸和失败清理；本轮正常教材元数据对照不能代替这些回归。

Outline 的书签读取已经主动管理文件流；Foundation 与 Visual Region 已用 closing 管理 PDFium 文档、页面和 bitmap。应沿统一资源规则检查，不机械替换所有渲染路径。

## 3. Practice：重复全书重建影响多个功能

`PracticePrototype.catalog()` 每次调用 `build_catalog()`；`question()` 为找单题也会先构建完整 catalog。收藏列表会为每本有关联的书重新构建 catalog。

本书一次带 profile 的提取约有 **39476 次 JSON 解码**，解码约占一半时间。普通重复提取约 630–780ms；收藏记录读取约 575–802ms。单独的作答记录读取只有约 2–3ms，主要成本不在作答记录表。

已有 `build_catalog(..., section_id=...)` 可复用：

- 1.2.6：约 17–21ms。
- 5.2.4：约 12–14ms。
- 另一节：约 45–70ms。

三节各自与全书构建的对应结果完全一致，包括内部题目、答案、解析和几何数据。

Hint 的源码路径分别通过 `question_source()` 和 `visual_context()` 查题；两者都会调用 `question()`。Review、提交和收藏也使用同一查题路径。因此应在共享查询处消除重复，不分别给每个按钮做零散缓存。

复用结果必须随 source revision、OCR 和 Outline 的变化失效。公开 Solve 投影与含官方答案的内部材料继续分开，提交前 AI context 的限制保持原样。

## 4. 学习状态与阅读上下文

`LearningRepository.entries()` 返回约 330 KiB 的投影，普通调用约 125–168ms，约 88 条业务 SQL。profile 中 SQL 执行本身约 5ms，主要耗时是 `add_display_ends()` 重新读取和推导整本书的位置，约 19030 次 JSON 解码。只减少 SQL 条数不会消除主要成本。

阅读上下文接口为得到当前章的学习数量也会调用完整 entries。可以让章统计使用保留发布版本过滤规则的轻量读取，把几何投影按 OCR / KP 来源变化复用，动态学习状态另行读取。现有稳定来源范围、批注锚点及掌握状态语义都应保持。

## 5. 搜索

348 页书的常见词搜索约 380–680ms，最多返回 100 页；未命中约 220–293ms，仍会扫描全书文字。常见词路径约 102 次数据库连接，其中 100 次用于命中页位置。

隔离的串行实验让一次搜索复用读取连接，同组从约 624–678ms 降至 246–266ms，返回结构完全一致。实验中的临时方法替换不是可直接并发上线的实现；正式代码应传递操作范围内的读取事务或批量取数。

现有 SQLite 足以继续优化。需要保留 NFKC、空白、跨行命中、100 页限制和 match_ranges，避免提速后搜索语义变化。

## 6. 显示、侧栏与高 DPI

普通连续滚动采样 90 帧，p95 约 16–19ms；本轮没有看到普遍的长时间卡顿。实际渲染和 OCR 叠层截图已目检。

侧栏定向性能脚本记录：Assistant / Guide 大多数状态变化约 1–14ms，首帧约 9–20ms。宽度变化时重画可见页符合现有布局，不应将这些正常节点更新直接算作缺陷。

**该性能门槛未通过**：打开 Master 测到 60ms 长任务，resize 测到 52ms；脚本在 50ms 阈值检查处失败。没有把它写成全项通过。可在后续检查历史消息的 Markdown / 数学排版复用与集中更新，优先级低于前述资源累积。

画布尺寸推算的 RGBA 容量：

| 显示条件 | 当前保留画布合计 |
| --- | ---: |
| DPR 1，100% | 约 27 MiB |
| DPR 1，200% | 约 90 MiB |
| DPR 1，400% | 约 360 MiB |
| DPR 2，100% | 约 108 MiB |
| DPR 2，200% | 约 360 MiB |

这是像素缓冲的尺寸容量，不是已经测得的 CPU 常驻内存或显存，未复现 OOM。高 DPI / 高缩放时缩小邻页预绘制范围值得验证，当前页保留原清晰度；OCR DPI 和来源坐标无需随之改变。

## 7. AI、本地裁图与网络

- Visual Region 同一区域重复裁图：首次含依赖加载约 350ms，之后约 91–99ms；样本 JSON 含约 812 KB 的 PNG base64。Hint / Review 会重做相同题图，可考虑只为当前题保留有边界的临时裁图复用。
- Assistant / Master 流式阶段已经增量追加文本，不是每个 token 全量重跑 Markdown。完成后及打开历史的重建才需要进一步 profile。
- 正常 Master 与 Practice Review 会带当前 topic 历史；当前样本消息规模不大。长对话的 token 与首字耗时需要用现有 runtime 指标另测，本轮没有重新调用真实 Provider，不能量化网络、上传和模型推理各自占比。
- PDF 已支持 Range。五轮开关与翻页中观察到数百至上千条 PDF 请求；正确释放加载任务也会取消旧任务的后续工作。当前静态资源与 PDF 都是 no-store，Handler 使用默认 HTTP/1.0。分片大小、连接与版本化静态缓存值得单独对照，尚未证明应采用哪套参数。
- 静态 JS 在单个 SPA 会话里只加载一次，本机传输快；它没有成为本轮最主要的等待项。AI 和用户材料的缓存边界不应随静态缓存一起改动。

## 8. 后台、存储及已有合理实现

- 准备完整的临时书库启动到 READY 约 0.7 秒；这是本机 Python 服务，不是安装版桌面壳的完整冷启动。
- 停留页面的 5 秒观察中，服务累计 CPU 约 0.188 秒，即单核约 3.75%，并出现 3 个请求；仍有后台活动，不作为完全静置的功耗测试。后台空轮询可继续观察，目前不是优先项。
- 原 PDF 画布已只保留可见页附近，OCR 页发布、可见页优先及 SSE 已存在。PDFium 的共享锁有线程安全依据，OCR 推理已经在锁外进行。
- SQLite 已用 WAL，基础书库、目录上下文和单页 overlay 大多为几毫秒到十几毫秒。160.5 MiB 的样本数据库约有 33.6 MiB 空闲页，可作为以后离线维护事项；没有证据需要每次启动压缩数据库。
- 章节 AI 作业与页面准备共享 worker，长作业可能延后新可见页；这是源码层的待验证风险。本轮未做有付费调用的排队实验，不将其列为已复现故障。
- OCR 的后端与精度结果来自此前独立的 CPU 跟进实验，没有重复跑一遍、将 OCR 结论推广到全部界面，或调整默认后端；该实验及报告留在实验工作区，不随本轮通用性能 checkpoint 发行。

## 下一轮建议

1. 先统一释放前端 PDF 加载任务和后端校验 reader/stream，覆盖正常、失败、取消和快速切书。
2. 再收敛 Practice 的共享查题路径，复用按节提取与有明确失效条件的结果。
3. 接着减少学习几何投影重算、搜索连接开销。
4. 最后根据高 DPI 真实体验决定邻页像素预算，并单独测真实 AI 首字延迟与历史渲染。

本轮未实测其他机器、安装包冷启动、低内存极限或官网网络，不承诺所有设备得到相同比例收益。现有 Practice UI、目录、Master 持久化和阅读显示均未改动。
