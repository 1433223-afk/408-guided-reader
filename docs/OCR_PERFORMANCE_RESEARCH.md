# 扫描 PDF OCR 性能调研（2026-09-28）

## 可比口径

- PaddleOCR 官方检测、识别模块表明确写明：延迟只计**模型推理**，不含前后处理；识别模型的数字针对一张已经裁出的文字区域，并非一整页 PDF。PP-OCRv5 mobile 识别在官方 Xeon Gold 6271C、8 线程环境的 CPU 标准模式为 21.20 毫秒/裁剪区域，高性能模式为 5.32 毫秒/区域；高性能模式会选用 Paddle/OpenVINO 等最优后端。检测模块另有耗时，不能把单行数字当整页数字。
- 王道实测样本一页常有约 50–99 行，仅按官方 21.20 毫秒/区域就约为 1.1–2.1 秒的识别推理，还未计 PDF 渲染、整页检测、方向分类、裁剪、逐词位置框、阅读顺序和入库。项目实测逐行识别约 2.1 秒/页，属于相同数量级；主流宣传中的几十毫秒不是同等工作量。本项目真实阅读功能还要求逐词位置框，而官方模块表没有承诺这个输出的端到端耗时。
- “高性能模式”约 5.32 毫秒/区域指出可验证的提速方向是推理后端与整批文字行处理，但这个数字来自不同模型、硬件和软件栈，不能直接移植到 RapidOCR + PP-OCRv6 small。后续需要单独检查 Paddle 静态推理或其他 CPU 后端在同一模型、同一教材页上的端到端表现。
- RapidOCR 作者的同机对比在 Apple M2、单张测试图、PP-OCRv5 mobile 模型下，RapidOCR + ONNX Runtime 约 0.93–1.26 秒/图，PaddleOCR CPU 约 1.75–1.93 秒/图。作者也注明单图测试粗略，不能代表不同分辨率图像。本项目使用 PP-OCRv6 small、200 DPI 教材整页及文字框，不能将这些数字直接当作教材页速。
- PaddleOCR 官方的 PP-OCRv5 mobile 模块表给出 CPU 文字检测 57.77 毫秒/图、文字识别 21.20 毫秒/裁剪文本行（标准模式，8 线程）；模块延迟不能直接相加为 PDF 整页延迟。
- OCRmyPDF 按页并行，优先用 pypdfium2 栅格化；其性能文档按像素量和并行任务数估算内存，未给通用的“页/分钟”承诺。它也避免对已有可靠文本层的页强制 OCR。

## 本机实测

硬件为 Ryzen 7 8845H，8 核 16 线程；样本为《王道 2026 操作系统》扫描页。当前输出包括文字与选择所需的位置框。下述小样本结果只用于定位瓶颈，不代表四本书总体质量或速度。

- 串行阶段约 20.5 页/分钟；安全的双页并行后，真实后半册约 29–32 页/分钟。371 页已全部完成，失败 0 页。
- 抽取 8 页：PDF 打开、探测和渲染平均约 85 毫秒；OCR 平均约 2771 毫秒，其中检测约 550 毫秒、方向分类约 40 毫秒、逐行识别约 2100 毫秒。常规样本每页只调用一次基础 OCR，没有触发项目的可选质量重试。
- 3 页小样本：识别批次 6（默认）总计 7.85 秒；批次 12 为 9.39 秒，24 为 10.95 秒，3 为 7.83 秒。增加批次还带来少量文本差异，不适合直接全局调整。
- 同 3 页从 200 降到 150 DPI，OCR 总耗时仅降低约 5%，有一页识别行数从 67 降到 64；不能用降低分辨率作为通用提速方案。
- 关闭逐词位置框在 3 页样本约快 19%，但会损害原文精确选择和题目定位，不能直接关闭。ONNX Runtime 每模型 3 个线程比 4 个线程在 3 页单任务样本约快 6%，2 个线程慢约 32%。进一步用操作系统和数据结构各 8 页、双页并行测试：4 线程为 32.7 页/分钟、占用约 7.13 核；3 线程为 30.6 页/分钟、占用约 5.38 核，16 页识别文字完全一致。3 线程给交互留出更多 CPU，但没有提高全书速度，因此暂不修改默认值。
- 再从王道四本书各抽 4 页，以相同 PP-OCRv6 模型、200 DPI 和逐词位置框比较页任务并发。2 页 × 4 线程为 28.51 页/分钟、约 6.84 核；3 页 × 3 线程两次分别为 31.40 和 28.94 页/分钟、约 7.48 和 7.08 核；4 页 × 2 线程为 29.96 页/分钟、约 6.50 核；3 页 × 2 线程为 28.79 页/分钟、约 5.11 核。16 页文本行数和文本哈希在这些配置中全部一致。三页配置的收益落在短样本波动范围，CPU 占用更高；四页也未带来稳定的大幅提速。这里仅计已渲染图像的基础 OCR，不包含 PDF 打开、入库及质量重试，因此不能替代真实导书体验测试。
- 模型替换试验：同一批 16 页、双页并发、每任务 4 个 CPU 推理线程，PP-OCRv5 mobile 检测和识别约 16.16 页/分钟，现用 PP-OCRv6 small 约 32.71 页/分钟；前者全部 16 页的文本和位置框均发生变化，且速度显著退步，因此不切换。首次由两个线程同时下载同一模型时曾出现文件打开竞争；模型文件最终 SHA256 与官方清单一致，正式计时在预下载后完成。
- 硬件加速探索：隔离安装 ONNX Runtime DirectML，仍使用现有 PP-OCRv6 模型。此台双 GPU 机器的单任务 16 页样本，设备 0 约 86.24 页/分钟，设备 1 约 46.82 页/分钟；两者相对 CPU 基线的 16 页文本、行框和逐词位置框完全一致。CPU 约 32.71 页/分钟。两个 DirectML 页任务同时初始化曾让 Python 进程以访问冲突退出，不能直接在当前同进程双 worker 中启用。设备编号的首次测试因参数未被正确传入而退回 CPU，其速度数字已废弃。以上仅证明这台机器的潜力，不能推断其他硬件速度。

## 同模型 CPU 后端试验

以下试验不修改 Reader 生产配置。OpenVINO 2025.4.1 与 PaddlePaddle 3.3.1 安装在仓库忽略的临时目录，使用同一 PP-OCRv6 small 模型、200 DPI 和逐词位置框。四本王道教材各 4 页的已渲染图像组成 16 页样本；双页并发、每模型 4 个推理线程。计时从模型预热之后开始，不包含 PDF 渲染、入库、质量重试和首轮模型编译；另记录预热约 4–5 秒。ONNX 基线的两次结果为约 29.3 与 32.7 页/分钟，短样本存在波动。

- 检测、分类、识别全部换为 OpenVINO：两次约 52.2 与 63.3 页/分钟。但 16 页中有两页比 ONNX 少检测到文字行；《计算机组成原理》的公式图示页从 77 行变 75 行，《计算机网络》一页从 51 行变 50 行。不能直接替换整套后端。
- 保留 ONNX 检测和分类，仅将识别换成 OpenVINO：约 46.1 页/分钟，16 页行数与行框完全一致，字符序列相似度均在 99.6% 以上。逐词位置框也不是逐字节一致；在两页细查中，一页 1012 个字词全部同文，坐标差均值约 0.02 像素、95% 坐标不变、最大 6 像素；另一页 905 个字词中约 865 个可逐个配对，坐标差均值约 0.03 像素、95% 不变、最大 6 像素。真实《数据结构》习题页的选项 A 把 `I、II` 识别成 `I、ⅡI`；原页可见为 `I、II`，因此该候选存在实际的习题文本退化。不能仅凭 40% 左右的短样本提速设为默认。
- Paddle 原生识别模型经 RapidOCR 适配层接入、仍保留 ONNX 检测时，一页 41 行样本约 17.8 秒；该适配层默认关闭 oneDNN。隔离试验开启 oneDNN 后约 3.34 秒，去掉每批推理后的内存收缩约 2.98 秒；相同页面当前 ONNX 约 2.47 秒、OpenVINO 识别约 1.48 秒。开启 oneDNN 后 CPU 消耗也更高。这个数字只能否定当前 RapidOCR→Paddle 接法，不能代表 PaddleOCR 官方高性能流水线。
- 所有实验和对照输出只留在忽略目录 `var/manual-browser/tmp/`，没有替换模型、依赖或 Reader 代码。

## 下一步方向

1. 当前实现允许 1–4 个页任务并发；12 个及以上逻辑处理器默认 2 页，每个任务的 ONNX Runtime 上限为 4 个线程。双页是兼顾 Reader 操作的默认值，不是代码或模型的硬上限。暂不因一次短样本把默认值调到 3 或 4。
2. PP-OCRv5 mobile 不符合提速目标，不接入生产。不要仅因模型名带 mobile 就假设会更快。DirectML 在本机有明显潜力，但多 worker 原生崩溃说明未来若接入，必须用单独进程隔离，先对本机设备短测再启用，异常时保留 CPU 路径；不同显卡仍需验证。它不是普通 CPU 用户的通解。
3. OpenVINO 仅替换识别是可继续验证的 CPU 候选，但必须解决真实习题选项误识别，并把四书正文、公式、目录、习题和逐词位置框纳入人工质量门槛。另需测完整 `prepare_page`、20 页冷启动、峰值内存和 UI 响应，短样本吞吐不能代替这些指标。PaddleOCR 官方高性能模式尚未复现；不应把 RapidOCR 的 Paddle 适配层结果等同于它。当前嵌入文字直取、可见页优先调度和按需准备应保留；不通过盲目增加并发、降低 DPI、增大识别批次或取消位置框追求表面页速。PDF 渲染只占约 3% 耗时。
