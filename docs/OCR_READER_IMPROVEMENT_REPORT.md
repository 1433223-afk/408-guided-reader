# Reader OCR 体验与调度改进（2026-09-28）

## 本轮改动

- 保持现有 PP-OCRv6、识别分辨率、质量重试和逐词位置框。Reader 顶栏按当前页显示待识别、识别中、可选或失败，并显示全书已完成页数；识别就绪后可见地提示“原书为准”，悬停说明原 PDF 可继续阅读以及可能存在漏字、错字。
- 翻页更新 OCR 优先级改为一次数据库更新。已有完整页任务时跳过整本书重复入队；已有完整 OCR 状态行时跳过逐页 `INSERT OR IGNORE`。重新打开被取消的任务时，未识别页面可以继续排队。
- 前 20 页目录和页码映射改为按进度合并刷新，目录工作移到独立后台线程，不再占用页面 OCR 工作线程。并发完成时仍保证首批页面全部就绪后有最终刷新。

## 验证与边界

- `tests/test_jobs.py`、`tests/test_foundation.py` 通过；涵盖双 worker 并发、最终目录刷新、目录阻塞时 OCR 继续运行、取消后续跑、翻页优先级和失败页重试。
- `node --check src/reader_service/static/app.js` 通过。用现有 312 页真实扫描教材运行 `tests-e2e/reader.mjs`：导入、翻页、缩放、重开和当前页状态提示通过，相关 API 无非预期失败。
- 独立的 600 页任务验证中，单次优先级更新约从 14.1 ms 降至 0.4 ms。这只衡量排队请求；目录刷新解耦和跳过重复写入已由行为测试确认，**尚未测得整本 OCR 完成时间的改变量**。单页模型推理仍是主要耗时；普通 CPU 上全书首次识别仍需时间。

下一步以真实用户导入过程观察首个可选页面等待时间、翻页响应和长任务稳定性；只有这些仍不达标时，再决定是否推进已隔离研究的 CPU 推理后端。不要把短样本后端吞吐当成产品实际速度。

## 2026-09-29 进度显示与提交前审核

用户已人工验收 OCR 实时页数修复。原进度流约 25 秒后主动结束，却声明保持连接；Reader 只依赖浏览器自动重连。现改为明确关闭旧连接，断线后先读取持久化状态再重建流，重连不重复排队。已完成或失败且没有活动任务时停止连接；失败页被重新排队时保持同一进度流。

提交前沿导入、排队、页状态、SSE、切书与失败重试检查，补齐两处边界：短暂读取错误恢复后清除残留错误提示；失败页重试时在同一数据库事务中重置页状态，使快速再次失败也能恢复重试按钮。切书时沿用 revision 与 generation 双重校验，旧连接和定时器随 Reader 关闭。

隔离书库的真实浏览器验证使用 312 页《计算机网络》扫描 PDF，75 秒内显示从 0 增至 41/312 页，期间建立 3 条进度连接，显示与持久化 READY 页数一致。`tests/test_jobs.py`、`tests/test_foundation.py`、`tests/test_api.py` 和 `tests-js/preparation-loading.test.js` 的相关检查通过。没有更换 OCR 模型，也没有测得整本书完成时间；首次全书识别仍需要后台处理时间。
